# METKA — статус проекта

Обновлено: 2026-10-19

## Архитектурные решения
- [ADR-001](docs/ADR-001-building-recognition.md): одна ONNX-эмбеддинг-модель для iOS/Android/web, кандидаты сужаются геолокацией, решение о награде принимает сервер (pgvector + PostGIS).
- [ADR-002](docs/ADR-002-server-game-logic.md): игровая логика — транзакционные Postgres RPC (SECURITY DEFINER), не Edge Functions.
- Стек: Vue 3.5 + TS 6 (strict) + Vite 8 + Pinia 4 + Vue Router 5 + SCSS, шрифт Inter (локально, @fontsource-variable/inter; как в Figma), Capacitor 8, Яндекс Maps JS API 3.0 (загрузка скриптом, типы `@yandex/ymaps3-types`), Supabase JS 2, onnxruntime-web 1.30. TS 7 не используется: vue-tsc пока его не поддерживает.
- [ADR-003](docs/ADR-003-map-buildings.md): карта из трёх слоёв — подложка Яндекс JS API v3 (решение владельца; MapLibre удалён 2026-10-18), контуры зданий из OSM (`osm_buildings`), игровой каталог `buildings` со ссылкой `osm_building_id` и `publish_status`.
- [ADR-004](docs/ADR-004-camera-scan.md): экран «Сканировать» (`/scan`) — живая камера + GPS + компас + контуры OSM, здание определяется приблизительно (статусы и ручной выбор), ничего не открывает; награда — только через `/scan/:buildingId`. Организации — `osm_pois` (миграция 012), связь со зданием только по попаданию в контур или вершине контура.
- Районы = территории
- Три независимые сущности: `explored_cells` (территория, миграция 008), `player_buildings` (здания, только скан), `memories` (альбом, миграция 010; одно воспоминание на игрока и здание, только для открытого здания). Прогресс — `player_progress()`: каждая цифра из своей таблицы; район засчитан от 50 ячеек.
- Исследованная территория (2026-10-18): своя сетка ≈22×22 м (`floor((lat+90)/0.0002)`, `floor((lng+180)/0.00036)`, одинаково в TS и SQL) вместо H3 — H3 нет в PGlite, его наличие в Supabase не подтверждено, а сервер обязан сам пересчитывать ячейки. Клиент шлёт только точки GPS; `record_exploration` (миграция 008) валидирует и сам открывает ячейки. Трекинг только в переднем плане. (отдельной таблицы `territories` нет).
- Платформенные различия изолированы в `src/services/*` за интерфейсами; выбор реализации — в `src/app/providers/services.ts`.

## Реализовано
Регистрация по шагам: заставка → знакомство → аккаунт (почта или OAuth) → подтверждение (код или ссылка, повторная отправка) → игровой профиль (никнейм + аватар-пиктограмма, `/auth/setup`, обязателен до входа в игру — guard в роутере) → разрешения в контексте (геолокация — пояснение перед системным запросом на карте, камера — при первом скане). Индикатор шагов «Шаг N из 3» в `AuthLayout`. Лоадер — чередование 4 пиктограмм (`FigureLoader`): на заставке под логотипом и в состояниях загрузки. Авторизация (email, восстановление, OAuth по конфигу, deep links, истечение сессии), профиль, карта (bbox-загрузка, районы с прогрессом, позиция, карточки), сканер (полный поток и ошибки), коллекция (поиск, фильтр), задания (прогресс, получение награды), кланы (создание, вступление, выход, рейтинг), лидерборды (RPC), жизненный цикл приложения.

## Не проверено / блокеры
- **Модель распознавания отсутствует.** Нет обученной модели и эталонных эмбеддингов реальных зданий. В production сканер честно показывает «распознавание недоступно». Нужны датасет и оценка по критериям ADR-001.
- **Код подтверждения почты** не проверен на реальном Supabase: шаблон письма «Confirm signup» должен содержать `{{ .Token }}` (см. README); `verifyOtp` с `type: 'email'`.
- **Supabase (проверено 2026-10-18 по наличию RPC):** миграции 002, 004, 005, 006, 007 применены; 003 (данные округов) анонимным ключом не проверить. 007 применялась вручную через SQL Editor; функция `import_osm_buildings` затем заменена исправленной версией. История `supabase_migrations` CLI не ведётся — `supabase db push` попытается применить их повторно.
- **Аватары кланов (миграция 005, не применена):** Storage-бакет `clan-avatars` (публичное чтение, ≤512 КБ, WebP/JPEG), загрузка/удаление только лидером в папку своего клана (RLS, проверено в PGlite с эмуляцией Storage). **Нет модерации** — картинки видны всем игрокам; нужна до публичного релиза (жалобы/ручная проверка/автомодерация). При удалении клана файл аватара остаётся в бакете (удалить из SQL нельзя) — нужна периодическая очистка.
- **Фото-аватары игроков (миграция 006, не применена, 2026-10-16):** бакет `profile-avatars` (как у кланов), запись только в папку `<user id>/` (RLS), `profiles.avatar_path` меняется только через RPC `set_profile_avatar` (проверяет папку и наличие файла). Колонка `profiles.avatar_url` (клиент мог писать любую https-ссылку → утечка IP других игроков) **удалена**. Фото приоритетнее пиктограммы `avatar_key`. **Нет модерации** — то же ограничение, что у кланов. Применять миграции строго по порядку: 006 после 005.
- **Android-сборка:** нет Android SDK и JDK 21 (есть только Java 8). Gradle не запускался.
- **iOS-сборка:** нет Mac и Xcode.
- Не проверено на устройствах: камера, GPS, возврат из фона, deep links.
- Конкурентные гонки при приёме скана защищены UNIQUE-ограничениями, но многопоточный тест невозможен в PGlite (одно соединение).
