# ADR-001. Архитектура распознавания зданий

Статус: принято для MVP · 2026-10-15

## Задача

Подтвердить, что игрок сфотографировал **конкретное** здание из каталога (instance-level recognition), а не «какое-то здание». Каталог MVP — десятки–сотни объектов в одном городе. Здания одной серии (панельки П-44, «сталинки») визуально почти идентичны.

Это не задача классификации по категориям, а задача **поиска по изображениям (image retrieval)**: сопоставить снимок с эталонными фотографиями объектов-кандидатов.

## Рассмотренные варианты

| Критерий | A. Общая модель (ONNX), один контракт | B. Нативные реализации (Core ML+Vision / ML Kit, TFLite) |
|---|---|---|
| Код | Одна модель, один пайплайн предобработки, один контракт результата | Две реализации, две предобработки, риск расхождения скорингов |
| Готовые нативные API | — | Vision/ML Kit не умеют распознавать *конкретные* здания «из коробки»; нужна своя модель в любом случае |
| Запуск | onnxruntime-web (WASM/WebGPU) в WebView: iOS, Android, веб; позже — нативный ORT/Core ML/NNAPI за тем же интерфейсом | Нативно, с аппаратным ускорением |
| Скорость (оценка, не замер) | 100–400 мс на один кадр для модели ~5–25 МБ на современных телефонах | 20–100 мс |
| Размер | Одна модель для всех платформ (int8 5–25 МБ) | Две сборки модели, две конвертации |
| Сервер | Та же модель (onnxruntime-node/python) повторно вычисляет эмбеддинг — сравнимые результаты | Нужна третья реализация на сервере |
| Стоимость | Низкая: вычисление на устройстве, сервер — сравнение векторов в pgvector | Выше: поддержка трёх стеков |

Ключевой довод: ни Vision, ни ML Kit не дают готового распознавания конкретных зданий, т.е. своя модель нужна в обоих вариантах. Раз модель своя — выгоднее одна модель и один контракт. Скорость нужна на **одном снимке**, а не на видеопотоке 30 fps, поэтому ускорение нативными движками — оптимизация, а не обязательное условие.

## Решение

**Вариант A: одна эмбеддинг-модель + поиск ближайших соседей + серверное решение.**

1. **Модель.** Эмбеддинг-модель для retrieval (глобальный дескриптор, GeM-pooling, L2-нормализация), экспорт в ONNX, квантизация int8.
   - Базовая линия для оценки: DINOv2 ViT-S/14 (сильный retrieval без дообучения, но тяжелее).
   - Целевой вариант: MobileNetV3/EfficientNet-Lite, дообученные с ArcFace на Google Landmarks v2 и собственных фото каталога.
   - Выбор подтверждается только замерами на собственном датасете (см. «Критерии качества»). **Готовой проверенной модели сейчас нет.**
2. **Эталоны.** Для каждого здания хранятся 5–30 эмбеддингов эталонных фото (`building_reference_embeddings`, pgvector), с привязкой к `model_version`.
3. **Сужение пространства поиска геолокацией.** Кандидаты — только здания в радиусе ~300 м от игрока. Это убирает основную часть путаницы «похожих фасадов»: две одинаковые панельки в разных районах никогда не конкурируют.
4. **Похожие фасады рядом.** Решение принимается по top-1 *и* по отрыву (margin) от второго кандидата; при малом отрыве — «не уверены, снимите ближе/под другим углом». Фаза 2: геометрическая верификация локальных признаков (ORB/SuperPoint + RANSAC) против эталонов для кандидатов с малым margin.
5. **Сервер решает сам.** Клиент присылает эмбеддинг снимка, модель-версию, хэш изображения, координаты и точность. Сервер сам считает сходство с эталонами целевого здания и соседей (pgvector), сам проверяет дистанцию (PostGIS) и принимает решение. Клиентские `candidates` и `confidence` используются только для UX и аналитики; в решении о награде не участвуют.
6. **Изображение.** Сжатый снимок загружается в приватный bucket `scan-photos` для аудита и фазы 2 (повторный серверный инференс той же ONNX-моделью). В MVP загрузка опциональна и выключена по умолчанию: это решение о хранении персональных данных (на фото могут быть люди), которое требует согласия пользователя.

## Поток данных

```
Карта → выбор здания (buildingId)
  → проверка разрешений (камера, геолокация)
  → снимок (CameraService, системная камера)
  → контроль качества кадра (размытие: дисперсия Лапласиана; яркость)
  → эмбеддинг (BuildingRecognitionService → EmbeddingModel/ONNX)
  → локальное сравнение с эталонами ближайших зданий → кандидаты (для UX)
  → GeolocationService: координаты + accuracy
  → Edge Function `submit-scan` (JWT, idempotency key)
       ├ аутентификация, rate limit
       ├ здание существует и активно
       ├ дистанция ≤ radius + допуск по accuracy (PostGIS)
       ├ сходство эмбеддинга с эталонами target vs соседи (pgvector): score ≥ T и margin ≥ M
       └ RPC `confirm_building_discovery` (одна транзакция):
            building_scans, player_buildings (UNIQUE), reward_ledger (UNIQUE),
            опыт/валюта/влияние/задания
  → ответ: accepted | rejected(reason) | duplicate
  → UI: карта, коллекция, профиль
```

## Контракт (TypeScript, `src/services/recognition/types.ts`)

`BuildingRecognitionService.recognize(input, { signal, timeoutMs })` → `RecognitionResult`:
`status: 'recognized' | 'ambiguous' | 'not_recognized' | 'poor_quality' | 'unavailable'`, `candidates[] {buildingId, score}`, `bestCandidate`, `margin`, `embedding`, `modelVersion`, `quality {blurScore, brightness}`, `diagnostics {durationMs, imageWidth, imageHeight}`. Диагностика не содержит координат, EXIF и самого изображения.

Ошибки — типизированные `RecognitionError` (`timeout`, `aborted`, `model_unavailable`, `decode_failed`).

## Если модель не настроена

`OnnxBuildingRecognitionService` возвращает `status: 'unavailable'`, сканер показывает понятное сообщение, сервер отклоняет скан с причиной `recognition_unavailable`. **Фиктивного успешного распознавания в production нет.** `MockRecognitionService` лежит в `src/mocks/`, подключается только при `import.meta.env.DEV && VITE_USE_MOCKS === 'true'`. Сервер принимает эмбеддинги только известных `model_version` из таблицы `recognition_models` (`is_active = true`); mock-версия засеивается только в `seed.sql` для локальной разработки.

## Ограничения защиты (честно)

- **GPS подделывается** (mock location, эмуляторы, джейлбрейк). Дистанция — фильтр, а не доказательство. Смягчение: проверка `accuracy`, лимиты частоты, проверка скорости перемещения между сканами (фаза 2), Play Integrity / App Attest (фаза 2).
- **Эмбеддинг подделывается**: клиент может прислать вектор, посчитанный по фото из интернета или по эталону. Смягчение в MVP: эталоны не отдаются клиенту целиком (только для зданий поблизости), rate limit. Фаза 2: загрузка фото и повторный серверный инференс, проверка на дубликаты (perceptual hash), выборочная модерация.
- **Фото экрана/распечатки**: в MVP не детектируется. Фаза 2: liveness-эвристики (муар, отражения), серия кадров.
- Вывод: в MVP награда подтверждается совокупностью сигналов на сервере, но устойчивой защиты от мотивированного читера нет. Ценность наград должна это учитывать.

## Датасет

```
dataset/
  buildings.csv                      # building_id, name, lat, lon, address_verified (bool)
  <building_id>/reference/*.jpg      # эталоны: 5–30 шт.
  <building_id>/eval/*.jpg           # отложенная выборка, не пересекается с reference по дням съёмки
  negatives/*.jpg                    # соседние здания вне каталога, похожие фасады
```

Правила: разные время суток, погода, расстояние 10–80 м, углы ±45°, без лиц крупным планом (или с размытием), ≥ 1024 px по меньшей стороне, EXIF с GPS удаляется перед публикацией. Метка — `building_id` из каталога; одна фотография — одно здание; фото, где целевое здание занимает < 30 % кадра, — не берём в эталоны.

## Критерии качества (до включения наград за реальные здания)

На eval-выборке каталога пилотного района:
- top-1 accuracy среди кандидатов в радиусе 300 м ≥ 95 %;
- false accept (негатив принят как здание) ≤ 1 % при выбранных T и M;
- p90 времени распознавания на устройстве среднего класса (Android 2021 г.) ≤ 1,5 с;
- размер модели ≤ 25 МБ.

## Статус

Реализованы контракт, пайплайн (камера → качество → эмбеддинг → сравнение), ONNX-адаптер с конфигурируемой моделью, серверная проверка и тесты. **Не реализовано:** обученная модель и реальные эталонные эмбеддинги. Распознавание реальных зданий не проверено.
